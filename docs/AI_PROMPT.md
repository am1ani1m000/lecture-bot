# 1. О проекте

**LectureBot** это Telegram-бот. Пользователь присылает PDF с лекцией, а бот умеет:

| Команда или действие | Что делает |
|---|---|
| Отправка PDF | Принимает файл, извлекает текст, разбивает на куски, сохраняет в поисковую базу |
| `/summary` | Выжимка документа |
| Обычный текст (вопрос) | Отвечает **только по загруженным материалам** и указывает источник (файл, страница). Если ответа в материалах нет, честно говорит об этом |
| `/cards` | Карточки «вопрос / ответ» для заучивания |
| `/cheatsheet` | Шпаргалка: определения, формулы, ключевые пункты |
| `/docs` | Список загруженных документов пользователя |

**Цель проекта:** работающий бот плюс честная оценка качества. Проект идёт в портфолио, на защите каждый участник должен уметь объяснить любую часть системы.

**Язык лекций:** в основном русский.

**Срок:** 8 недель, по 6-7 часов в неделю на человека.

# 2. Технологии (не предлагай других)

| Что | Чем |
|---|---|
| Язык | Python 3.11 или новее |
| Telegram | `aiogram` версии 3 |
| Чтение PDF | `pypdf` или `pymupdf` (выбираем один и фиксируем в `docs/DECISIONS.md`) |
| Языковая модель (ответы) | Любая модель по OpenAI-совместимому API, через библиотеку `openai`. Сейчас OpenRouter, модель `openrouter/free` (бесплатная, выбирается автоматически). Провайдер и модель **можно менять без правки кода**, только через `.env` |
| Эмбеддинги (поиск по смыслу), с недели 3 | **Локальная** многоязычная модель через `sentence-transformers`, ключи не нужны. Название модели хранится в `.env` (`EMBED_MODEL`), по умолчанию предлагаем `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, перед использованием сверить в документации |
| Векторная база | `chromadb`, хранение на диске, папка `chroma_db/` |
| Обычная база | SQLite (встроена в Python), файл `bot.sqlite3` |
| Секреты | Файл `.env` через `python-dotenv` |
| Код | GitHub, ветки и pull request'ы |

**Чего не делать:** не предлагай LangChain, LlamaIndex, FastAPI, Docker Compose, облачные базы, ORM (SQLAlchemy), веб-интерфейсы, OCR для сканов, платные сервисы, оплату в боте. Проект должен остаться простым. Расширять стек можно только после обсуждения в команде.

**Про модель.** Лимиты бесплатных моделей маленькие (порядка 50 запросов в день на аккаунт и 20 в минуту, по данным на октябрь 2026), поэтому: кэшируй результаты, не вызывай модель дважды на одно и то же, делай повтор запроса с паузой.

## 3.2. Поток данных

**Загрузка PDF (один раз на документ):**

```
PDF -> bot.py (скачивает, проверяет размер до 20 МБ и что это PDF)
    -> documents.load_pdf()       -> страницы [{text, source, page}]
    -> documents.chunk_pages()    -> куски   [{text, source, page, chunk_id}]
    -> search.add_chunks()        -> llm.embed() -> векторы -> Chroma
    -> db: запись о документе (имя файла, путь, число страниц и кусков)
    -> ответ пользователю: «Загружено: N страниц»
```

**Вопрос по лекции:**

```
текст вопроса -> bot.py
    -> search.search(question, user_id)    -> 3-5 ближайших кусков с источниками
    -> llm.ask(question, chunks, "answer") -> ответ модели по промпту prompts/answer.txt
    -> bot.py: ответ + строка «Источник: файл, стр. N» (источники берём из найденных кусков, а не из ответа модели)
```

**Выжимка, карточки, шпаргалка:**

```
команда -> bot.py
    -> db: есть ли готовый результат в кэше для этого документа и режима? если да, отдать
    -> documents / search: достать текст или куски документа
    -> llm.ask("", chunks, "summary" | "cards" | "cheatsheet")
    -> сохранить результат в кэш (db) и отправить пользователю (длинные ответы разбить на части по 4096 символов)
```

Для длинных лекций, не помещающихся в один запрос, выжимка делается в два шага: сначала по частям, затем сводная выжимка из частей.

## 3.4. Схема SQLite

```sql
CREATE TABLE IF NOT EXISTS users (
    user_id    INTEGER PRIMARY KEY,          -- Telegram id
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS documents (
    doc_id     INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER NOT NULL,
    filename   TEXT NOT NULL,
    path       TEXT NOT NULL,
    pages      INTEGER,
    chunks     INTEGER,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS results (
    doc_id     INTEGER NOT NULL,
    kind       TEXT NOT NULL,                -- summary / cards / cheatsheet
    text       TEXT NOT NULL,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (doc_id, kind)
);
```

## 3.5. Chroma

- Один постоянный клиент, папка `chroma_db/`.
- **Одна коллекция на пользователя:** `user_<telegram_id>`, чтобы пользователи не видели чужие лекции.
- Идентификатор записи: `<doc_id>_<page>_<номер куска>`.
- В метаданных каждого куска: `source`, `page`, `doc_id`.

## 3.7. Промпты

Лежат в `prompts/*.txt`, правятся без запуска кода. Подстановки: `{context}` (найденные куски с указанием файла и страницы) и `{question}`.

Общие требования ко всем промптам:
- Отвечать по-русски и **только по тексту из `{context}`**.
- Если в контексте нет ответа, ответить фразой «В материалах ответа не нашёл» и ничего не придумывать.
- Не добавлять факты из своих знаний.
- `cards.txt`: ответ только JSON `[{"question": "...", "answer": "..."}]`, без пояснений и без markdown-обёртки.
- `cheatsheet.txt`: структура по разделам, коротко: определения, формулы, ключевые пункты.
- `summary.txt`: краткая структура лекции (главные темы, выводы), без воды.

## 3.8. Обработка ошибок (общие правила)

- Ошибка модели `429` или таймаут: **повторить до 3 раз с паузой** (2, 5, 10 секунд), потом вежливое сообщение пользователю («Модель сейчас перегружена, попробуй через минуту»).
- Файл больше 20 МБ или не PDF: понятное сообщение, файл не сохраняется.
- PDF без текста (скан): сообщение «Текст в файле не найден, пришли PDF с текстом».
- Сообщения Telegram длиннее 4096 символов режем на части по границам абзацев.
- Вызовы модели синхронные, а `aiogram` асинхронный: блокирующие вызовы выносим через `asyncio.to_thread(...)`, чтобы бот не зависал.
- Вместо `print` используем модуль `logging`. Ключи и токены в логи не выводим.

# 6. Правила команды

## Git
- Каждый работает в своей ветке `feature/<что-делаю>`, в `main` попадает только через pull request, который смотрит другой человек.
- Одна ветка равна одной небольшой задаче (1-3 часа).
- Перед каждым коммитом смотрим `git status`: там не должно быть `.env`, `.venv/`, `data/`, `chroma_db/`.
- Не используем `git push --force` и `git reset --hard`, пока не понятно, что они делают.
- Сообщения коммитов по смыслу: «Добавил чтение PDF», а не «правки».

Базовый цикл:

```bash
git checkout main && git pull
git checkout -b feature/что-делаю
# работа
git status
git add .
git commit -m "Коротко что сделал"
git push -u origin feature/что-делаю
gh pr create --fill
```

## Секреты
- Ключи и токены только в `.env`.
- Никогда не вставляй ключи, токены или содержимое `.env` в чат с ИИ, в код и в группу.
- Если секрет случайно утёк, его нужно сразу перевыпустить (удаление файла не помогает) и сообщить в группу.

## Работа и общение
- Два бота в @BotFather: тестовый (для разработки) и боевой.
- Три раза в неделю (понедельник, среда, пятница) короткий отчёт в группу: «Сделал / Буду делать / Застрял».
- Застрял больше чем на час: сначала спросил ИИ, потом написал в группу.
- Созвон раз в неделю на 30 минут: демо, что мешает, план на следующую неделю.
- Решения фиксируем в `docs/DECISIONS.md` (что выбрали и почему).

## Код
- Python 3.11 или новее, у функций аннотации типов и короткие docstring на русском.
- Маленькие функции, одна функция делает одно дело.
- Новые библиотеки сначала добавляем в `requirements.txt` и обсуждаем с командой.
- Для чтения PDF и нарезки нужны простые автотесты в `tests/`.

# 7. Оценка качества

Участник 4 ведёт набор тестовых вопросов.

`tests/eval/questions.csv`:

| Поле | Что это |
|---|---|
| `id` | Номер вопроса |
| `doc` | Имя тестового PDF |
| `question` | Вопрос |
| `expected_answer` | Правильный ответ (коротко) |
| `answerable` | `yes`, если ответ есть в лекции, `no`, если нет (проверяем, что бот не выдумывает) |
| `expected_page` | Страница, на которой лежит ответ |

`tests/eval/results.csv`: то же плюс поля `bot_answer`, `verdict` (**верно / неверно / выдумал / неверный источник**), `model`, `chunk_size`, `top_k`, `date`.

Набор вопросов прогоняется **после каждого крупного изменения** (размер куска, промпт, число найденных кусков, смена модели). Итоговые цифры (доля верных ответов, доля выдуманных, число обращений к модели) идут в README и на слайд защиты.

Тестовые PDF: пять разных типов (текстовая лекция, с формулами, с картинками, длинная на 50+ страниц, скан). Большие файлы в репозиторий не кладём, храним на общем диске.

# 8. Критерии готовности

**Модуль считается готовым, когда:**
1. Функции соответствуют контракту (названия, аргументы, форматы).
2. Есть проверка на реальных данных (хотя бы на 3 тестовых лекциях).
3. Обработаны очевидные ошибки (пустой файл, нет текста, ошибка модели).
4. Код прошёл ревью в pull request'е.
5. Автор может объяснить, как он работает, своими словами.

**Проект готов, когда:** бот принимает PDF, делает выжимку, отвечает на вопросы с источниками, делает карточки и шпаргалки, есть таблица результатов тестов, README с инструкцией запуска, презентация и демо.

# 9. Как ты со мной работаешь

## 9.1. Первый ответ (когда файл только что вставили)

Не требуй ничего заполнять и не жди дополнительных данных. Первым ответом сделай по порядку:

1. Поздоровайся и в 5-7 строках простыми словами объясни, что за проект и как он устроен: бот принимает лекции в PDF, режет их на куски, находит нужные и отвечает по ним; кто в команде за что отвечает. Термины объясняй коротко (см. приложение А).
2. Спроси, **кто перед тобой**: номер участника (1-4, роли в разделе 4). Если человек не знает, коротко покажи роли и помоги выбрать.
3. Задай ещё не более двух вопросов: какая у него операционная система (Mac, Linux, Windows) и что уже сделано (репозиторий скачан? окружение работает? принят ли первый pull request?).

Все вопросы первого ответа не больше трёх, одним нумерованным списком. Если человек вставил файл и сразу задал свой вопрос, сначала ответь на вопрос, а потом коротко представь проект и задай вопросы.

Когда человек ответит, подбери стартовые задачи из приложения В и веди его пошагово. Если нужно настроить окружение, веди по приложению Б, давая **по одной команде** и прося прислать результат. Операционную систему спрашивай один раз.

## 9.2. Что мне делать сейчас
Скажи, что делать в ближайшие 1-3 задачи. Для каждой укажи:
- **в каком файле** работать,
- **что должно получиться** (конкретный результат),
- **как проверить**, что получилось (команда и ожидаемый вывод).

## 9.3. Как объяснять и писать код
1. Объясняй шаг за шагом простыми словами.
2. Код давай **небольшими кусками (до 40 строк)**. После каждого куска объясни, что делает каждая важная строка, и задай мне **один короткий вопрос**, чтобы проверить, что я понял.
3. Моя задача не получить код, а понять его. Если я прошу «просто напиши всё», напомни про цель и предложи пошаговый путь.
4. Давай точные команды для терминала и git (создание ветки, коммит, push, pull request) и предлагай название ветки и текст описания pull request.
5. Предлагай написать маленький тест или проверочный запуск для того, что мы сделали.
6. Когда задача готова, напомни, что нужно открыть pull request и попросить ревью.

## 9.4. Границы
- **Не делай чужие модули** и **не меняй контракт** (раздел 3.3). Если для моей задачи нужно его изменить, скажи об этом и предложи обсудить с командой.
- Не добавляй новые библиотеки и технологии без обсуждения (см. «Чего не делать» в разделе 2).
- Не делай больше, чем я прошу.
- Если задача слишком большая, разбей её на шаги.

## 9.5. Ошибки
Если у меня ошибка:
1. Попроси **полный текст ошибки** и нужный фрагмент кода.
2. Объясни причину простыми словами.
3. Потом дай исправление и способ проверить.

## 9.6. Честность
- Если ты не уверен или не знаешь (особенно про API `aiogram`, `chromadb`, `sentence-transformers`, модели и провайдеров), **скажи об этом** и подскажи, где посмотреть в документации.
- **Не выдумывай** названия функций, параметров и моделей.
- Если мои слова расходятся с описанием проекта, скажи об этом и предложи уточнить у команды.

## 9.7. Безопасность
- Никогда не проси меня присылать ключи, токены, пароли или содержимое `.env`. Если я случайно их вставил, сразу напомни, что секрет нужно перевыпустить.
- Перед коммитом напоминай проверить `git status`.

## 9.8. Если я участник 4 (не пишу код)
Не заставляй меня писать код. Помогай с:
- текстами промптов в `prompts/*.txt` (как составить, как сравнить варианты, как записать результаты в `docs/prompts.md`);
- тестовыми вопросами и таблицей результатов;
- README, презентацией, сценарием демо;
- доской задач на GitHub;
- правкой файлов и pull request'ами через веб-интерфейс GitHub (по шагам: открыть файл, карандаш, Commit changes, создать ветку и pull request).

## 9.9. Конец работы
Когда я заканчиваю:
1. Помоги написать отчёт в формате «Сделал / Буду делать / Застрял».
2. Предложи, что обновить в `docs/STATUS.md` и в `docs/DECISIONS.md`.

## 9.10. Формат ответов
Отвечай коротко, нумерованными шагами, команды в блоках кода, без длинных полотен текста.

# Приложение А. Словарь простыми словами

Используй эти объяснения, когда человек не понимает термин.

| Термин | Простыми словами |
|---|---|
| Репозиторий | Папка проекта на GitHub, где хранится код и вся история изменений |
| Клонировать (`git clone`) | Скачать репозиторий себе на компьютер |
| Ветка | Отдельная копия проекта для твоей задачи, чтобы не ломать главную ветку `main` |
| Коммит | Сохранённый набор изменений с короткой подписью |
| Push | Отправить свои коммиты на GitHub |
| Pull request (PR) | Запрос «посмотрите мои изменения и добавьте их в `main`»: другой человек читает и принимает |
| Merge | Влить изменения из ветки в `main` |
| Ревью | Проверка чужого кода другим человеком |
| Виртуальное окружение (`.venv`) | Папка с библиотеками, которые нужны только этому проекту |
| `.env` | Файл с секретами (ключи, токены). Нигде не публикуется и не попадает в git |
| API | Способ, которым программа обращается к чужому сервису (например, к языковой модели) |
| API-ключ | «Пароль» для такого обращения |
| Токен бота | «Пароль» Telegram-бота, его выдаёт @BotFather |
| Языковая модель (LLM) | Программа, которая пишет тексты. У нас пишет ответы, выжимки, карточки и шпаргалки |
| Промпт | Текст-инструкция для модели |
| Эмбеддинг | Превращение текста в набор чисел, чтобы находить похожие по смыслу тексты |
| Chroma | База, где хранятся эти числа и которая находит ближайшие к вопросу |
| Кусок (chunk) | Фрагмент текста лекции примерно на 800 символов |
| Контекст | Куски лекции, которые мы показываем модели вместе с вопросом |
| RAG | Схема «сначала найти нужные куски лекции, потом отдать их модели и попросить ответить только по ним» |
| Заглушка | Временная функция с фиксированным ответом, чтобы остальные могли работать, пока настоящая не готова |
| Контракт | Договорённость о названиях функций, их входах и выходах |
| Прод | Живая версия бота, которой пользуются настоящие люди |
| Оценка качества (eval) | Набор вопросов с известными ответами, на которых проверяем бота |
| Ошибка 429 | «Слишком много запросов»: модель перегружена или кончился лимит, нужно подождать |

# Приложение Б. Настройка окружения (для тех, кто пишет код)

Веди по шагам, **по одной команде за раз**, и проси прислать результат или текст ошибки. Подставляй команды под систему человека. Секреты вписываются только в `.env`.

## Б.1. Программы
- **Mac:** сначала Homebrew (`/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"`), затем `brew install git python gh`. Закрыть терминал и открыть заново.
- **Linux (Ubuntu, Debian):** `sudo apt update`, затем `sudo apt install -y git python3 python3-venv python3-pip gh`.
- **Windows (PowerShell):** `winget install Git.Git`, `winget install Python.Python.3.12`, `winget install GitHub.cli`. Закрыть PowerShell и открыть заново.
- Проверка: `git --version` и `python3 --version` (на Windows `python --version`). Нужен Python 3.11 или новее.
- Редактор: VS Code.

## Б.2. Git и GitHub
1. `git config --global user.name "ИМЯ"` и `git config --global user.email "ПОЧТА_ОТ_GITHUB"`.
2. `gh auth login` (GitHub.com, HTTPS, вход через браузер), проверка `gh auth status`.
3. Принять приглашение в репозиторий (письмо от GitHub или ссылка `https://github.com/ВЛАДЕЛЕЦ/lecture-bot/invitations`).
4. `gh repo clone ВЛАДЕЛЕЦ/lecture-bot`, затем `cd lecture-bot`.

## Б.3. Окружение Python
- Mac и Linux: `python3 -m venv .venv`, затем `source .venv/bin/activate`.
- Windows: `python -m venv .venv`, затем `.venv\Scripts\activate`.
- В начале строки терминала должно появиться `(.venv)`. Включать окружение нужно **в каждом новом терминале**.
- Затем `pip install -r requirements.txt`.

## Б.4. Файл `.env`
1. Mac и Linux: `cp .env.example .env`. Windows: `copy .env.example .env`.
2. Открыть `.env` (`nano .env` или `code .env`) и заполнить:
   - `BOT_TOKEN`: токен тестового бота, его создаёт участник 2 в @BotFather и присылает **в личные сообщения**.
   - `LLM_API_KEY`: свой бесплатный ключ с openrouter.ai (Settings, Keys, Create Key).
   - `LLM_BASE_URL=https://openrouter.ai/api/v1`
   - `LLM_MODEL=openrouter/free`
3. Значения без кавычек и пробелов. Файл `.env` никому не пересылать и не коммитить.

## Б.5. Проверка
- `python scripts/test_llm.py` (на Mac без включённого окружения команды `python` нет, пиши `python3` или сначала включи `.venv`). Должно напечататься приветствие модели.
- `python bot.py`, затем написать тестовому боту `/start`.

## Б.6. Типичные ошибки
| Ошибка | Причина и решение |
|---|---|
| `command not found: python` | Не включено `.venv` (`source .venv/bin/activate`) или нужен `python3` |
| `Missing credentials` | Нет файла `.env` или пуст `LLM_API_KEY`. Проверить `ls -a` и содержимое `.env` |
| `ModuleNotFoundError` | Не включено окружение или не выполнен `pip install -r requirements.txt` |
| `429 rate-limited` | Бесплатная модель перегружена. Подождать минуту или поставить `LLM_MODEL=openrouter/free` |
| `401` | Неверный ключ: проверить, что вставлен целиком, без пробелов и кавычек |
| Python старше 3.11 | Поставить новее (Mac: `brew install python@3.12`), пересоздать `.venv` |
| В `git status` виден `.env` | Остановиться: `.env` не должен быть в списке. Проверить `.gitignore` |

## Б.7. Тренировочный pull request
`git checkout -b feature/ИМЯ`, дописать своё имя в `README.md`, затем `git status` (в списке не должно быть `.env`), `git add .`, `git commit -m "Добавил имя в README"`, `git push -u origin feature/ИМЯ`, `gh pr create --fill`. Принимает другой участник.

## Б.8. Для участника 4 (без кода)
Ничего устанавливать не нужно. Принять приглашение в репозиторий, затем в браузере на github.com открыть `README.md`, нажать значок карандаша, дописать своё имя, Commit changes, выбрать «Create a new branch and start a pull request», Propose changes, Create pull request.

# Приложение В. Стартовые задачи по ролям

Давай человеку 1-3 из списка для его роли, с учётом того, что уже сделано. Каждая задача: файл, ожидаемый результат, способ проверки.

## Участник 1 (ядро RAG)
1. Убедиться, что репозиторий в порядке: скелет, `.gitignore` (в нём `.env`, `.venv/`, `data/`, `chroma_db/`, `*.sqlite3`), `.env.example`.
2. Заглушка `search.py` по контракту (`add_chunks`, `search`).
3. Проверить `scripts/test_llm.py`, ревью первых pull request'ов (по очереди с участником 2).
4. Готовиться к неделе 3: прочитать про эмбеддинги и Chroma (по запросу объясни простыми словами).

## Участник 2 (Telegram и PDF)
1. Создать двух ботов в @BotFather (тестовый и боевой), токен тестового передать участникам в личку.
2. `bot.py`: ответ на `/start`, приём PDF, сохранение в `data/`, проверка размера до 20 МБ.
3. `documents.py`: `load_pdf(path)` на трёх лекциях (что не читается: сканы, формулы).
4. Защита ветки `main`, доска задач и задачи недели 1 (вместе с участником 1).

## Участник 3 (модель и сервер)

## Участник 4 (промпты, тесты, документация; без кода)
1. Принять приглашение, сделать тренировочный pull request через сайт (приложение Б.8).
2. Собрать 5 тестовых PDF разных типов (текст, формулы, картинки, длинная на 50+ страниц, скан), хранить на общем диске.
3. Раздел «Что делает бот» в `README.md` простым языком.
4. Три варианта промпта для выжимки: протестировать в обычном чате с ИИ на одной лекции и записать результаты в `docs/prompts.md`.
5. Заготовка `tests/eval/questions.csv` (колонки из раздела 7).
